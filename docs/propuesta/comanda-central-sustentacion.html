Dos infraestructuras distintas

Para desarrollar

  • PC del desarrollador con Docker Compose
  • API, PostgreSQL y Redis en contenedores locales
  • Frontend PWA en servidor de desarrollo
  • Git y GitHub · colección de pruebas de API

Una PWA con Service Worker solo funciona bajo HTTPS: el certificado no es opcional, es requisito del navegador.

Para producción

  • contenedor proxy inverso, workers y servicios de negocio
  • máquina los dos servidores de aplicación
  • administrado PostgreSQL con réplica y Redis
  • por consumo CDN y almacén de objetos
  • incluido monitoreo, logs centralizados y respaldos diarios

La base de datos y la caché conviene contratarlas administradas: ahí el proveedor asume respaldos, réplica y parches.

PostgreSQL como almacén principal

Datos y aislamiento entre clientes

Por qué relacional

  • Una venta afecta pedido, detalle, pago, documento fiscal e inventario a la vez: se confirma completa o no se confirma
  • La numeración fiscal debe ser consecutiva y sin huecos por sede, y las restricciones lo garantizan
  • Los reportes por sede, producto, canal y franja horaria son consultas SQL naturales
  • Nueve mil transacciones diarias no justifican una base distribuida NoSQL, y adoptarla sacrificaría la consistencia que el caso fiscal exige

Redis para sesiones, menús calientes y el canal Pub/Sub que alimenta los WebSocket. Almacén de objetos para los XML fiscales y las imágenes.

Multi-tenant

Una sola instalación atiende a muchas cadenas con sus datos aislados.

Cadena A  →  Sede 1 · Sede 2 · Sede 3
Cadena B  →  Sede 1 · Sede 2

Columna cadena_id más Row Level Security de PostgreSQL. La restricción vive en el motor, no en el código: aunque un desarrollador olvide un filtro, la base filtra igual.

Caja en línea
El POS opera contra el servidor central. Cada venta se registra en línea.
  • La PWA ya está cargada: el POS no depende de la red para seguir funcionando
  • Cada venta se guarda en IndexedDB con un identificador único generado en la sede
  • El consecutivo fiscal sale del rango pre-asignado a esa sede, así dos sedes nunca lo repiten
  • Al volver la conexión la cola se envía por lotes y el servidor compara los identificadores
  • Si una respuesta se perdió y la sede reenvía, llega el mismo identificador y el servidor no duplica la venta

Eso es idempotencia, y es lo que hace que reintentar sea seguro. Sin internet no carga el menú QR ni entran pedidos de Rappi: lo que se protege es la sala y la caja, que es donde está el dinero.

Dos transacciones por segundo las mueve cualquier servidor moderno. El reto real de este sistema es la disponibilidad y la sincronización.

Por eso el requisito que le ponemos al restaurante no es contratar más megas: con menos de 100 kbps por sede basta. Es instalar un router con conmutación automática a 4G.
